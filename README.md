# WP Multilang Press

> **Ведёте сайт, а не разрабатываете плагин?** Вам нужна [инструкция пользователя](docs/user-guide.md) — установка, настройка языков и перевод статей без единой строки кода. Этот файл написан для тех, кто плагин дорабатывает.

WordPress-плагин мультиязычности, построенный по модели TranslatePress:

```
1 запись WordPress  +  N языковых URL  +  переводы строк в своих таблицах
```

Дубли постов не создаются. Плагин перехватывает уже отрисованный HTML, разбирает его в DOM, подставляет переводы из базы и отдаёт готовую страницу на `/en/...`. Поэтому переводится всё, что реально вывела тема: тексты, меню, шапка, подвал, виджеты, формы, подписи к картинкам — а не только содержимое записи.

Текущее состояние — **Этапы 1, 2 и часть Этапа 3**. Перевод по-прежнему вводится вручную — но теперь можно попросить ИИ (OpenAI) предложить перевод одной кнопкой, проверить его и сохранить самому. Никакой автоматики: плагин не переводит сайт целиком сам и не ходит в OpenAI в фоне.

## Что умеет сейчас

- Языки сайта: код, URL-слаг, статус `опубликован` / `черновик`, язык по умолчанию.
- Языковые адреса: `/about/` — русский, `/en/about/` — английский. Язык определяется только по URL, без cookie.
- Один канонический 301: лишний префикс языка по умолчанию и неверный регистр слага. Черновой язык отдаёт 404.
- Серверный перевод готового HTML: текстовые узлы, `alt`, `title`, `placeholder`, `aria-label`, надписи кнопок, `<title>` и meta description.
- Автоматический сбор строк: страницы, открытые на дополнительном языке, пополняют словарь.
- **Визуальный редактор**: предпросмотр страницы рядом с панелью перевода, выбор текста кликом, сохранение без перезагрузки.
- **«Перевести весь материал с ИИ»**: заголовок, анонс и всё содержимое записи одной операцией — вместо перевода блок за блоком, с автоматической разбивкой на части и проверкой перед сохранением.
- **Translation blocks**: абзац, разорванный тегами `<b>` и `<a>`, переводится целиком вместе с разметкой.
- **Перевод интерфейса без ручного труда**: на дополнительном языке плагин подменяет локаль WordPress, и ядро, тема и плагины сами отдают свои строки из официального языкового пакета — «Ответить», «Оставить комментарий», кнопки корзины переводятся без единой строки в базе и без единого токена OpenAI.
- Админка «Перевод строк»: три вкладки — «Контент», «SEO/GEO» и «Интерфейс», фильтры по языку и статусу, поиск, ручной ввод перевода.
- Удаление переводов: по одной строке и все переводы выбранного языка сразу.
- Переключатель языков: один пункт в меню WordPress (выпадающий список или в ряд, с emoji-флагами), шорткод `[mlp_language_switcher]` и виджет.
- Ключ OpenAI хранится в базе данных, вводится в админке — доступ к файлам хостинга не нужен.
- На дополнительном языке в списках показываются только переведённые записи.
- Мультиязычная карта сайта со взаимными `hreflang` для поисковиков.
- Перевод SEO-разметки: meta description, Open Graph, Twitter Card, `article:*`, JSON-LD (`inLanguage`, заголовки, хлебные крошки) — с защитой идентификаторов, адресов картинок и имён брендов.
- Заголовок записи переводится один раз и одинаково подставляется в `<title>`, H1, `og:title`, `twitter:title` и JSON-LD `headline` — без риска разных формулировок в разных местах.
- Логотип сайта (`Organization.logo` в JSON-LD) не меняет `@id` между языками — так же, как сама организация; изображение самой записи это не задевает.
- Внутренние ссылки в футере темы и других жёстко закодированных блоках получают языковой префикс так же, как построенные через WordPress.
- В «Перевод строк» — фильтр «Тип», отдельно собирающий SEO/GEO-поля.
- Базовое SEO: self-canonical, взаимный hreflang с `x-default`, атрибут `lang`.
- **Перевод с ИИ**: кнопка рядом с полем перевода — и в списке строк, и в визуальном редакторе — заполняет поле подсказкой от OpenAI. Ничего не сохраняется автоматически: перевод нужно проверить и нажать «Сохранить» самому. Дневной лимит символов защищает от случайных расходов.

Чего пока нет: автоматической фоновой очереди перевода, обхода ВСЕГО САЙТА одной кнопкой (массовым переводом кнопкой охвачена одна запись целиком, не весь каталог), glossary и translation memory, истории правок с откатом, замены картинок и ссылок для конкретного языка, перевода slug, sitemap-адаптеров, поддержки WooCommerce, gettext и динамического JS-контента.

## Требования

| Компонент | Версия |
|---|---|
| PHP | 8.1+ (рекомендуется **8.4+**) |
| WordPress | 6.4+ |
| MySQL / MariaDB | MySQL 8 / MariaDB 10.6+ |
| Постоянные ссылки | любая структура, кроме «Простые» |

На PHP 8.4+ используется встроенный HTML5-парсер `\Dom\HTMLDocument` — быстрый и корректный. На 8.1–8.3 плагин переключается на libxml `DOMDocument`: он тоже работает, но на нестандартной разметке точность ниже.

**Зависимостей в рантайме нет.** Папку `vendor/` заливать на хостинг не нужно: если автозагрузчика Composer нет, плагин подключает собственный PSR-4 загрузчик.

## Установка

1. Скопируйте папку плагина в `wp-content/plugins/wp-mlp` (имя папки может быть любым).
2. Активируйте «WP Multilang Press» в разделе «Плагины». При активации создаются четыре таблицы и настройки по умолчанию: русский как основной язык, английский на `/en/`.
3. Откройте «Настройки → Постоянные ссылки» и нажмите «Сохранить» — это пересоберёт языковые правила адресов.

Если структура постоянных ссылок стоит «Простые», плагин покажет предупреждение: языковые URL при ней не работают.

## С чего начать и в каком порядке

Если коротко: **один раз настроить, потом переводить только свой текст.** Интерфейс сайта переводится сам, и большую часть списков трогать не нужно вообще.

### Один раз, при установке

1. **«Мультиязычность → Языки»** — добавьте языки. В каждой строке проверьте **«Локаль WordPress»** (`bg_BG`, `en_US`): это имя, под которым WordPress ищет переводы своего интерфейса. Оно подставляется автоматически, но `en` может значить и `en_US`, и `en_GB` — угадать нельзя.
2. Там же, рядом с локалью, — индикатор **языкового пакета**. Если написано «пакета нет», нажмите «Скачать языковой пакет». Без него интерфейс останется английским, и будет казаться, что плагин не работает. Английскому пакет не нужен.
3. Проверьте: откройте любую страницу на `/bg/`. Меню, форма комментариев, кнопки должны стать болгарскими **без единого действия с вашей стороны**. Если стали — самое главное уже работает.

### Дальше — на каждую новую статью

4. Напишите статью на основном языке как обычно.
5. **«Мультиязычность → Визуальный редактор»**, выберите язык и страницу → «Открыть».
6. Нажмите **«Перевести весь материал с ИИ»** — заголовок, анонс и весь текст одной операцией. Проверьте предложенное и нажмите «Сохранить всё».
7. Пройдитесь по странице глазами. Что осталось непереведённым — кликните прямо в превью и впишите перевод.

Этого хватает в 90% случаев. Всё, что ниже, — для остального.

### Когда что-то осталось непереведённым

Откройте **«Мультиязычность → Перевод строк»** и выберите вкладку по тому, **что именно** не переведено:

| Что видите на сайте | Вкладка | Кто это написал |
|---|---|---|
| Текст статьи, заголовок, пункт меню, подпись к картинке | **Контент** | вы |
| «Ответить», «Оставить комментарий», кнопка корзины | **Интерфейс** | WordPress, тема или плагин |
| Ничего не видно, но неверно в Google или при отправке ссылки | **SEO/GEO** | SEO-плагин |

Правило простое: **писали сами — «Контент», не писали — «Интерфейс»**.

### Что можно не делать никогда

- Не переводите на вкладке «Интерфейс» строки админских плагинов (Rank Math, Akismet, Action Scheduler). Их надписи видите только вы в админке, посетитель — никогда. Смотрите на колонку «Источник».
- Не ищите строки заранее: список наполняется, только когда страница реально показана на дополнительном языке. Пустой список означает «ещё не открывали», а не поломку.
- Не переводите заголовок записи дважды. Он общий для H1, `<title>`, соцсетей и микроразметки — переводится один раз во вкладке «Контент».

### Если список засорился

Кнопка **«Очистить строки без перевода»** внизу каждой вкладки убирает найденные строки, у которых нет ни одного перевода. Переведённое не трогает, а нужное соберётся заново при следующем показе страниц. Полезно, если в список попал мусор — например, вы ходили по сайту до установки языкового пакета.

## Как пользоваться

### Добавить язык

«Мультиязычность → Языки»: заполните код (`de`), URL-слаг (`de`), название (`Deutsch`), при желании emoji-флаг (`🇩🇪`) и статус. Сохраните — правила адресов пересоберутся сами.

- **Опубликован** — язык доступен посетителям и попадает в `hreflang`.
- **Черновик** — язык виден только в админке: его URL отдаёт 404, в `hreflang` его нет. Удобно, пока перевод не готов.

Язык по умолчанию отдаётся без префикса и черновиком быть не может.

Флаг — необязательное поле, плагин не подставляет его сам: код языка не всегда однозначно связан со страной (у английского нет «своего» флага), поэтому выбор оставлен за вами. Флаг появится перед названием в переключателе языков.

### Перевести страницу в визуальном редакторе

Самый быстрый способ, когда нужно перевести конкретную страницу.

1. «Мультиязычность → Визуальный редактор». Либо откройте нужную страницу на сайте и нажмите «Перевести страницу» в верхней панели.
2. Выберите язык и при необходимости укажите путь страницы, например `/about/`.
3. В предпросмотре справа наведите курсор — переводимые места подсветятся рамкой. Нажмите на нужное.
4. Слева появятся оригинал и поле перевода. Впишите текст, нажмите «Сохранить» (или Ctrl+Enter) — текст в предпросмотре заменится сразу.
5. Переходите по ссылкам прямо в предпросмотре: режим редактора сохраняется.

Кнопка «Удалить перевод» очищает перевод только этой строки.

### Перевести весь материал с ИИ

Для конкретной записи или страницы — вместо перевода блок за блоком кликом по каждому узлу.

1. «Мультиязычность → Визуальный редактор», откройте запись (путь должен указывать на реальный пост/страницу — на архивах и служебных страницах кнопки не будет).
2. Кнопка «Перевести весь материал с ИИ» открывает выбор: **«Только пустые сегменты»** (по умолчанию — не трогает то, что уже переведено) или **«Перевести заново весь материал»** (перезаписывает всё, включая уже подтверждённые переводы, — сознательный выбор, не значение по умолчанию).
3. Плагин разбирает заголовок, анонс (excerpt) и `post_content` записи, показывает прогресс по частям (материал автоматически делится на части под контекстное окно модели — вручную ничего разбивать не нужно) и заполняет поля перевода прямо в панели. Каждая переведённая строка сразу показывается в предпросмотре справа.
4. Список — черновик, а не готовый результат: любую строку можно поправить вручную прямо в панели, как и статус.
5. «Сохранить всё» пишет весь список одной операцией. Если сохранение прервётся ошибкой — не сохранится ни одна строка из этой операции, а то, что уже было переведено раньше (вручную или в прошлый раз), не тронется.

`post_content` в базе не меняется вообще — ни во время перевода, ни после «Сохранить всё»: как и везде в плагине, перевод живёт в отдельной таблице `wp_mlp_translations` и подставляется только при показе страницы посетителю. Заголовок, анонс и содержимое разбираются на сегменты со стабильным `uniq_hash` — тем же способом, что и обычная страница (ТЗ 4.4), — но источником служат сами поля записи, а не отрисованный HTML: комментарий-обёртка `<!-- wp:... -->` не переживает рендер блоков (ядро вырезает его при показе), значит взять его получится только из `post_content` напрямую.

Формат того, что вокруг переведённого текста, не трогается ни на символ — и это не «мы стараемся не менять лишнего», а следствие способа подстановки: перевод каждого сегмента ищется в исходной строке как точная подстрока и заменяется на своём месте, без разбора и повторной сборки HTML. Всё остальное копируется из исходника один в один, включая то, что раньше портил любой инструмент, реконструирующий разметку через DOM: самозакрывающиеся теги (`<img ... />` не превращается в `<img ...>`), точный стиль кавычек и порядок атрибутов, Gutenberg-комментарии с JSON-параметрами, классы, инлайн-стили, `id`, `data-*`, ссылки и изображения. Если точную подстроку для сегмента найти не удаётся (например, символ в тексте закодирован непривычной HTML-сущностью) — операция для этого поля явно останавливается, а не подставляет перевод «примерно туда».

Если в тексте есть шорткод вперемешку с обычными словами (`Нажмите [button url="/x"]здесь[/button]`), ИИ просят не трогать сам тег. Проверка после ответа — не «похоже на тот же тег», а точное сравнение всей последовательности шорткодов: имена, порядок, вложенность, атрибуты и их значения. Если ответ модели содержит хоть одно расхождение — эта строка не попадает в предложенный перевод (нужно перевести вручную), а если каким-то образом испорченный перевод всё же дойдёт до сохранения — всю операцию «Сохранить всё» целиком отклонит уже сервер, не записав ни одной строки из неё.

Строки, для которых заголовок/анонс/содержимое совпадают с уже переведёнными в другом месте сайта, повторно переводить не нужно: словарь общий (см. «Перевести строку списком» ниже). При следующем изменении записи повторный запуск найдёт только то, что реально изменилось с прошлого раза (сравнение по `uniq_hash` с сохранённым слепком прошлого перевода записи) — остальной готовый перевод не сбрасывается.

Строки глобальных элементов темы (меню, футер, виджеты) и SEO/GEO-поля (meta, Open Graph, JSON-LD) сюда не входят намеренно — это по-прежнему инструмент «Перевод строк» ниже, у записи и у сайта в целом разные экраны перевода.

**Атомарность «Сохранить всё».** Проверка пакета и сама запись в базу — два независимых шага. Сначала весь присланный список проверяется целиком, без единого обращения к базе на запись: неизвестный или чужой (принадлежащий другой записи) идентификатор строки, задвоенный идентификатор, испорченный шорткод — любая из этих находок останавливает всё, ни одна строка не сохраняется. Только после того, как проверка пройдена целиком, начинается сама запись — одной SQL-транзакцией: если посреди неё откажет база данных, откатываются и уже записанные в рамках этой операции строки. Ранее сохранённые переводы (из прошлых операций) эта проверка не трогает, пока текущая не завершится успехом целиком.

Если ошибка «проверка пакета не прошла» называет `foreign_segment` для строк, которые точно принадлежат этой же записи, — это была реальная ошибка (исправлена 09.08.2026): запись «места использования» строки не учитывала, к какой именно записи она относится, только сам факт «встречалась при массовом переводе». Если одна и та же фраза (общий абзац-заготовка, повторяющийся в нескольких статьях) встречалась при массовом переводе НЕСКОЛЬКИХ записей, право владения ею оставалось только у той, что была разобрана последней, — остальные записи не могли подтвердить, что фраза принадлежит и им тоже, и «Сохранить всё» отклоняло весь пакет. Починка обратно совместима сама: при следующем открытии «Визуального редактора» для задетой записи её строки перерегистрируются правильно, без каких-либо действий с базой данных вручную.

**Что проверено автоматически, а что — нет.** Разбор записи на сегменты, подстановка перевода точной подстрокой (включая память о самозакрывающихся тегах и HTML-сущностях), разбивка на части, выбор режима «только пустые»/«перевести заново», полная проверка пакета перед записью (чужой/неизвестный/задвоенный идентификатор, испорченный шорткод), построение «мест использования» с учётом id записи (см. выше про `foreign_segment`) и вся цепочка «разбор → несколько частей → проверка → запись → повторное чтение», включая две записи с общим абзацем, — покрыты юнит- и интеграционными тестами (`tests/Rendering/PostContentExtractorTest.php`, `tests/Rendering/RawContentPatcherTest.php`, `tests/Rendering/SegmentLocatorTest.php`, `tests/Rendering/PostFieldPatcherTest.php`, `tests/Support/ShortcodeGuardTest.php`, `tests/Translation/PostCommitValidatorTest.php`, `tests/Translation/BulkTranslationModeTest.php`, `tests/Translation/PostOccurrenceRowsTest.php`, `tests/Integration/PostBulkTranslationChainTest.php`) и гоняются без установленного WordPress. Не покрыто автоматически и требует ручной проверки на установленном плагине: сам REST-роутинг, `permission_callback`/nonce поверх настоящего WordPress, и поведение реальной SQL-транзакции (`START TRANSACTION`/`ROLLBACK`) на живом MySQL при сбое посреди записи — без настоящего сервера баз данных это не воспроизвести.

### Перевести абзац целиком

Иногда абзац разорван тегами: `Читайте <b>наш</b> блог` — это три отдельных куска, и перевести их по отдельности грамотно нельзя, потому что порядок слов в языках разный.

Нажмите на такой абзац в редакторе — под полем перевода появится кнопка «Перевести абзац целиком». После нажатия абзац становится одной строкой, и переводить его нужно вместе с разметкой: `Read <b>our</b> blog`.

Разрешены только оформительские теги (`b`, `i`, `a`, `span`, `img`, `br` и подобные). Скрипты, стили и обработчики событий вырезаются.

### Перевод интерфейса: WordPress, тема и плагины

Строки вроде «Ответить», «Ваш адрес email не будет опубликован», «Обязательные поля помечены *» или кнопок корзины **не нужно переводить руками**. Они уже переведены сообществом WordPress и лежат в языковых пакетах — плагину достаточно сказать ядру, что текущая страница на другом языке.

Как это работает: на дополнительном языке подменяется локаль WordPress (`locale`, `plugin_locale`, `theme_locale`), и ядро, тема и плагины сами возвращают свои строки из `wp-content/languages/`. Ни одной записи в базе, ни одного запроса в OpenAI.

**Что нужно сделать один раз:**

1. «Мультиязычность → Языки», колонка **«Локаль WordPress»** — проверьте значение (`en_US`, `bg_BG`, `ru_RU`). Оно предзаполнено по коду языка, но угадать можно не всё: британскому английскому нужен `en_GB`, а у каталанского локаль вообще без региона — `ca`.
2. Там же — индикатор языкового пакета. Если написано «Языкового пакета нет», нажмите **«Скачать языковой пакет»**: без файлов перевода ядро вернёт английские оригиналы, и подмена локали внешне «не сработает». Для английского пакет не нужен — WordPress везёт его с собой.

**Английский особый**: на `/en/` эффект виден сразу и без скачивания, потому что оригиналы строк WordPress и есть английский текст. Для болгарского без пакета интерфейс останется английским — это не поломка, а именно отсутствие пакета.

**Вкладка «Интерфейс»** в «Переводе строк» — для того, что официальный пакет не покрыл: у нишевого плагина может не быть перевода на нужный язык вовсе. Там же можно переопределить неудачную формулировку из официального перевода — ваш вариант всегда главнее пакета, а кнопка «Сбросить к официальному» возвращает пакетный.

В списке видно, откуда строка («WordPress (ядро)», «Плагин: Easy Digital Downloads»), её контекст и форму множественного числа. Строки, которые пакет уже перевёл, в список не попадают намеренно: иначе он распух бы на тысячи строк ядра, и найти среди них требующие внимания стало бы невозможно.

**Что подмена локали НЕ трогает**: админку, AJAX, cron, REST и POST-запросы. Поэтому `wp-admin` остаётся на вашем языке, а транзакционные письма (уведомления о комментариях) уходят на исходном — их язык в этой версии не меняется вовсе.

Вместе с языком меняются формат даты, названия месяцев и направление текста — это часть локали, так и должно быть.

### Перевести строку списком

1. Откройте любую страницу сайта на дополнительном языке, например `https://site.ru/en/about/`. Плагин запомнит все найденные на ней строки.
2. Зайдите в «Мультиязычность → Перевод строк», выберите язык и при желании фильтр «Нет перевода».
3. Впишите перевод и нажмите «Сохранить» (или Ctrl+Enter).
4. Обновите страницу на дополнительном языке — текст заменится.

Строки появляются в списке **только после посещения страницы** на дополнительном языке: плагин переводит то, что реально вывела тема, и заранее знать этот список не может.

Одинаковый текст переводится один раз на весь сайт. Текст и значение атрибута считаются разными строками: «Купить» в кнопке и «Купить» в `alt` картинки переводятся отдельно.

Фильтр «Тип» разделяет строки на текст, атрибуты (`alt`, `title`, `placeholder`), блоки с разметкой и **SEO/GEO** — meta description, Open Graph, Twitter Card, `article:section`/`article:tag` и текстовые поля JSON-LD. Обычно эти поля разбросаны по всей странице вперемешку с обычным текстом; фильтр собирает их в один список, чтобы не искать вручную.

### Удалить переводы

- Ссылка «Удалить» в строке таблицы или кнопка в редакторе — убирает один перевод.
- Кнопка «Удалить все переводы языка» под фильтрами — убирает все переводы выбранного языка. Действие необратимо и спрашивает подтверждение. Исходные строки при этом остаются, удаляются только переводы.

### Переключатель языков

Три способа поставить его на сайт.

**В меню сайта (обычно то, что нужно).** «Внешний вид → Меню» → блок «Языки» слева → отметьте **одну** из двух галочек — «Выпадающий список» или «В ряд» — и нажмите «Добавить в меню». Больше ничего делать не нужно: под этим одним пунктом плагин сам подставляет реальные языки при каждом показе меню, ничего заранее вкладывать друг в друга не требуется.

```
«Выпадающий список» → пункты появляются по наведению/клику,
                       оформлением подменю вашей темы:

Главная  Блог  Контакты  Язык ▾
                          ├ 🇷🇺 Русский
                          └ 🇬🇧 English

«В ряд» → языки видны сразу, отдельными пунктами подряд:

Главная  Блог  🇷🇺 Русский  🇬🇧 English
```

Оба пункта можно добавить одновременно и оба можно переименовать/удалить как обычный пункт меню. У пункта «Выпадающий список» название («Язык») — то, что видно как заголовок; у пункта «В ряд» название значения не имеет, он сам становится первым языком.

**Шорткод** в контенте или шаблоне:

```
[mlp_language_switcher]
[mlp_language_switcher type="dropdown"]
[mlp_language_switcher show_current="no"]
```

**Виджет** «Переключатель языков» в «Внешний вид → Виджеты».

Черновые языки не показываются нигде: доступного адреса у них нет. Если единственный опубликованный язык — сам пункт меню, переключаться не на что, и плагин его не выводит вовсе.

Выпадающий список рассчитан на темы со стандартной разметкой подменю WordPress (`.sub-menu`, класс `menu-item-has-children`) — так работает подавляющее большинство тем. Для очень нестандартных мега-меню тема может не подхватить это автоматически; в таком случае свой класс на пункт-триггер можно добавить фильтром `mlp_nav_menu_dropdown_classes`.

### Карта сайта

Плагин отдаёт собственную карту по адресу `/wp-mlp-sitemap.xml`. В ней все языковые версии со взаимными `xhtml:link hreflang` — по ним Google понимает, что `/about/` и `/en/about/` это одна страница на двух языках, а не два дубля.

Непереведённые страницы в карту не попадают: их адрес на `/en/` отдаёт русский текст, и для поисковика это был бы дубль. Если у записи в карте нет пары на каком-то языке — это почти всегда означает «ещё не переведена на этот язык», а не ошибку: как только появится хотя бы один перевод (ручной или через «Перевести весь материал с ИИ»), её языковая версия сама появится в карте при следующей генерации.

У главной страницы теперь тоже есть `lastmod`: если она статическая (задана в «Настройки → Чтение»), берётся её собственная дата правки; если главная — лента последних записей, берётся дата самой свежей публично видимой записи сайта.

`lastmod` каждой записи считается по реальной дате изменения контента, а не по времени сборки карты: у языка по умолчанию это дата правки самой записи (`post_modified`), у остальных языков — эта же дата ИЛИ дата последнего изменения перевода, какая из них свежее. Перевод хранится не в самой записи, а в отдельной таблице, и обычная правка записи его не трогает: без этого сравнения `lastmod` английской версии страницы навсегда оставался бы датой последней правки русского текста, даже если сам перевод появился только сегодня.

Из карты сайта исключаются служебные страницы — определяется это не по слагу или названию, а по нескольким независимым признакам одновременно:
- страницы ролей WooCommerce — корзина, оформление заказа, личный кабинет (вместе со всеми вложенными — историей заказов, подтверждением, счётом, неудавшейся транзакцией и т. п.), если WooCommerce активен; каталог товаров (страница «Магазин») в это исключение не входит — это обычный, ценный для SEO раздел;
- страницы, защищённые паролем;
- страницы, явно помеченные `noindex` в Yoast SEO, Rank Math или SEOPress — тех же трёх плагинах, с которыми плагин уже совместим в остальном;
- страницы, слаг которых вписан вручную в «Мультиязычность → Языки → Исключить из карты сайта» — для случаев без WooCommerce и без отметки `noindex` (например, страница оформления заказа, собранная вручную без единого плагина корзины, или техническая страница вроде «Нет доступа»).

Совпадение любого из этих признаков исключает и саму страницу, и всё, что вложено под ней. Убрать что-то ещё программно, не через настройки (например, из отдельного плагина или снипета), можно фильтром `mlp_sitemap_post_ids` — он получает готовый список id записей прямо перед сборкой карты.

**Если проблемные адреса уже попадали в карту сайта раньше и Google успел их проиндексировать** (Search Console → Файлы Sitemap покажет число обработанных страниц) — одного лишь исправления карты недостаточно: Google не убирает страницу из индекса только потому, что она пропала из sitemap, это может занять недели. Чтобы ускорить: Search Console → Индексирование → Удаления → «Новый запрос» для каждого адреса, который не должен быть в выдаче.

Адрес автоматически добавляется в `robots.txt` одной строкой `Sitemap: ...`, так что поисковики найдут карту сами; повторно эта строка не добавляется, даже если что-то вызовет добавление ещё раз. Другие плагины (Yoast, Rank Math) могут дописать в `robots.txt` свою собственную строку `Sitemap:` — это нормально, несколько разных карт в одном `robots.txt` совместимы между собой, это не дубль одной и той же карты. Отправить карту вручную в Google Search Console — быстрее, чем ждать, пока её найдут сами. Ссылка есть в «Мультиязычность → Языки».

Карта не встраивается в sitemap ядра WordPress и не подменяет карты Yoast или Rank Math — она работает рядом с ними. Причина: рендерер карты сайта в ядре выводит только `loc` и `lastmod` и молча выбрасывает `xhtml:link`, то есть языковые версии туда просто не добавить.

### SEO-разметка и совместимость с Yoast / Rank Math

Переводится точный список полей — белый список, без wildcard-совпадений: `<title>`, meta description, `og:title`, `og:description`, `og:image:alt`, `article:section`, `article:tag`, `twitter:title`, `twitter:description`, `twitter:image:alt`, `twitter:label1`, `twitter:label2`, `twitter:data2`. `twitter:data1` в списке нет намеренно — там обычно лежит имя автора, имя собственное, а не текст для читателя. `og:site_name` в списке тоже нет намеренно: по спецификации Open Graph это название сайта целиком («CenterAI»), то же имя бренда, что и `name` у `Organization`/`WebSite` в JSON-LD, — оно уже защищено от перевода, и og:site_name защищён тем же способом: его отсутствие в белом списке. Остальные поля (`twitter:card`, `twitter:site`, `twitter:creator`, `article:published_time`, `article:author` и т. п.) не трогаются вообще — их нет в списке, и они остаются такими, как их вывел SEO-плагин. Переводимые строки попадают в общий список «Перевод строк» наравне с текстом страницы — их можно найти отдельно фильтром «Тип → SEO/GEO».

Отдельно правится то, что переводить нельзя, а нужно подменить: `og:url` и `twitter:url` указывают на языковой адрес, `og:locale` — на текущий язык в полном виде `xx_XX` (`ru_RU`, `bg_BG`, `en_US`), как того требует документация Facebook — голого двухбуквенного кода недостаточно. `og:locale:alternate` пересобирается по остальным языкам в том же формате. `og:image` не трогается никогда — если у SEO-плагина уже стоит изображение статьи, оно остаётся ровно тем же на любом языке; логотип сайта подставляется SEO-плагином только как запасной вариант, когда у записи своего изображения нет, — плагин в этот выбор не вмешивается вообще, только следит, чтобы адрес не сломался при подстановке языкового префикса.

**Один перевод заголовка записи — везде.** `<title>`, H1, `og:title`, `twitter:title` и JSON-LD `headline` в подавляющем большинстве конфигураций SEO-плагина несут один и тот же текст — заголовок записи. Раньше это были четыре независимо хешируемых сегмента (текстовый узел, два meta-атрибута, поле JSON-LD): перевести их можно было порознь, и итоговая страница вполне могла показать разные формулировки в вкладке браузера, в самом тексте и в превью соцсетей. Теперь `og:title`/`twitter:title`/`headline` при подсчёте ключа словаря приравниваются к обычному тексту — если их содержимое совпадает с текстом `<title>`/H1 (а оно совпадает всегда, если только заголовок SEO не переопределён шаблоном с суффиксом типа `%title% — %sitename%`), все они делят один и тот же ключ и один и тот же перевод, и подстановка сама достигает всех пяти мест сразу по одному переводу.

При этом в таблице `sources` такая объединённая строка хранится и находится фильтром «Тип → SEO/GEO» именно как SEO-поле, а не как обычный текст: `SegmentDeduplicator` — часть, отвечающая за выбор «представителя» при совпадении ключа словаря, — намеренно отдаёт предпочтение SEO-варианту (`og:title`/`headline`) перед H1/`<title>`, даже если в разметке HTML-узел встречается раньше по документу. Без этого приоритета побеждал бы почти всегда именно H1/`<title>` (они в `<head>`/начале `<body>`, а JSON-LD обычно ближе к концу `<head>`), и объединённая строка заголовка перестала бы находиться через фильтр SEO/GEO, оставаясь только в «Тексте».

**JSON-LD** (микроразметка Rank Math, Yoast): переводятся только заголовки и описания — `headline`, `description`, `name` в хлебных крошках и подобное. Имена собственные не трогаются: `name` у `Person`, `Organization` и `Brand` остаётся как есть, чтобы «CenterAI» не превратилось во что-то другое. `inLanguage` подменяется на код текущего языка. `url` внутри `WebPage`/`Article` получает языковой префикс, а вот `url` внутри `ImageObject`/`VideoObject`/`AudioObject` — никогда: это ссылка на файл в `wp-content/uploads`, он один на все языки, и добавленный префикс превратил бы её в несуществующий адрес. Двойная защита: по типу объекта и, независимо, по расширению файла — если тип в чужом графе указан неточно, спасает расширение.

Идентификаторы (`@id`) обрабатываются в два прохода, а не по месту в дереве:

1. Сначала строится карта ОПРЕДЕЛЁННЫХ сущностей графа — узлов, где `@id` стоит рядом со СВОИМ `@type` (`{"@type":"Organization","@id":"..."}`). `@type` при этом читается и как строка, и как список (`["Person","Organization"]`) — совпадения по любому элементу достаточно. Для каждой сущности решается новое значение `@id` по ЕЁ СОБСТВЕННОМУ типу: `Organization`/`Person`/`WebSite` (объект реального мира, один и тот же на любом языке) — без языкового префикса, всегда, на любом языке, включая язык по умолчанию; `WebPage`/`Article`/`BlogPosting`/`NewsArticle`/`BreadcrumbList` (конкретная языковая версия страницы) — с префиксом текущего языка, точно так же, как поле `url`. SEO-плагин обычно строит стабильный `@id` через `home_url()`, а этот вызов уже проходит через наш собственный фильтр языкового префикса раньше, чем страница доходит до разбора DOM — значит `@id` может прийти УЖЕ с чужим префиксом (`.../en/#organization`), и плагин не просто оставляет его как есть, а активно возвращает к каноническому виду.
2. Отдельно, тем же способом, находятся узлы, на которые ссылается свойство `logo` (`Organization.logo`, `Person.logo`) — независимо от их места в графе и вида ссылки (голая `{"@id":"..."}"` или полное inline-определение с собственным `@type": "ImageObject"`). Логотип сайта — такой же стабильный, не зависящий от языка актив, как сама Organization, но по одному `@type` его не отличить от изображения конкретной записи (`Article.image`): оба `ImageObject`. Разница — в том, что на логотип ссылаются ИМЕННО как на `logo`; изображение записи так не оформляется никогда, и его `@id`/`url` эта проверка не задевает.
3. Готовая карта «старое значение → новое» применяется ко ВСЕМ вхождениям `@id` в графе — не только там, где сущность определена, но и там, где на неё ссылаются: `"publisher":{"@id":"..."}"`, `"author":{"@id":"..."}"`, `"about"`, `"isPartOf"`, `"mainEntityOfPage"`. У такой ссылки своего `@type` обычно нет вовсе, и раньше это было источником бага: тип ссылки пытались определить по родителю в дереве (`Article` у `publisher`), а сама ссылка на организацию от этого организацией не становится. Теперь ссылка находит своё новое значение по совпадению самого `@id`, а не по структурной позиции.

Типы, для которых правило не определено и на которые не ссылается `logo` (например `ImageObject` — изображение самой записи), плагин не трогает вовсе — ни добавляет префикс, ни убирает: трогать то, что не понимаешь, опаснее, чем оставить как есть.

Совместимость с Yoast и Rank Math сделана не через их PHP-фильтры, а правкой готового HTML — того же, что уходит посетителю. Что бы они ни вывели, результат приводится к текущему языку, и обновление этих плагинов ничего не ломает.

### Внутренние ссылки и футер темы

Ссылки, построенные средствами WordPress (`get_permalink()`, пункты меню и т. п.), получают языковой префикс автоматически. Но тема может написать ссылку в шаблоне буквальным текстом — `<a href="/kontakty/">`, в обход этих функций. Такая ссылка часто встречается в футере, если он захардкожен в `footer.php`: без дополнительной обработки она вела бы на исходный язык, даже открытая с `/en/...`.

Отдельный проход по готовому HTML находит такие ссылки на свой домен и добавляет языковой префикс, если его ещё нет. Внешние домены, `mailto:`, `tel:`, якоря (`#section`) и уже прошедший через `home_url()` адрес не трогаются — как и файлы в `wp-content/uploads` (документы, картинки), у них один адрес на все языки.

Отдельный случай — пункты меню, сохранённые буквальным адресом ещё до того, как на сайте появился этот плагин (например `<a href="/ru/kontakty/">`, где `/ru/` — старый способ отмечать русский раздел). Если такую ссылку просто дописать спереди новым префиксом, получится `/en/ru/kontakty/` — двойная локализация. Плагин узнаёт первый сегмент пути как слаг ДРУГОГО известного языка и заменяет его на целевой, а не добавляет поверх.

Ссылки самого переключателя языков (пункт меню NavMenu, шорткод и виджет `[mlp_language_switcher]`) этот проход не трогает: каждая из них уже ведёт на СВОЙ язык, а не на язык текущей страницы, — они помечены классом `mlp-language-item` прямо на `<a>`, и по нему проход их пропускает. Без этой отметки переключатель на второй проход выглядел бы как обычная ссылка темы и получил бы префикс текущей страницы поверх уже правильного адреса — ru/bg/en вели бы в одно и то же место.

Текст в футере (копирайт, слоганы, любые фразы) переводится тем же общим механизмом, что и весь остальной текст страницы: `<footer>` для извлекателя строк ничем не отличается от `<main>` — никакого отдельного тега или флага для футера в коде нет и не требуется. Если фраза в футере на дополнительном языке всё ещё не переведена — это значит, что её ещё не перевели в «Перевод строк» (или на неё не долистали), а не что плагин её пропустил; заходить нужно на страницу с этим футером на нужном языке хотя бы раз — тогда строка появится в списке. Единственный практический нюанс: если в футере стоит виджет вроде «Последние записи», он показывает заголовки ДРУГИХ записей сайта их собственным текстом (обычно на исходном языке) — если для конкретной записи ещё нет перевода заголовка, в футере она покажется непереведённой, пока такой перевод не появится (тем же способом, что и у H1 — см. «Один перевод заголовка записи — везде» выше).

### Непереведённые записи

По умолчанию включено: на дополнительном языке блог, рубрики, метки и поиск показывают только записи, у которых есть хотя бы один перевод. Отключается в «Мультиязычность → Языки».

Отдельная запись при этом остаётся доступной по прямой ссылке — посетитель мог прийти из поисковика, и 404 вместо частично переведённой страницы был бы хуже.

Запись попадает в список только после того, как вы хотя бы раз откроете её на дополнительном языке: до этого плагин не знает, какие строки ей принадлежат.

## Подключение OpenAI (перевод с ИИ)

Без этого шага плагин работает как обычно — просто кнопки «Перевести с ИИ» не будет видно ни в списке строк, ни в редакторе. Доступ к файлам хостинга не нужен — всё через админку.

1. «Мультиязычность → Языки». В блоке «Ключ OpenAI» впишите ключ — <https://platform.openai.com/api-keys>.
2. Ниже — «Модель OpenAI»: точный идентификатор модели, сверьте с личным кабинетом или документацией OpenAI. «Адрес API» трогайте только для своего прокси/совместимого шлюза, по умолчанию `api.openai.com`.
3. Сохраните. В том же блоке появится «Ключ сохранён, заканчивается на «…»» — сам ключ повторно нигде не показывается, поле для ввода нового значения всегда пустое. Чтобы заменить ключ — впишите новый; чтобы оставить как есть — просто не трогайте поле при сохранении других настроек; чтобы удалить — отметьте «Удалить сохранённый ключ».
4. Задайте дневной лимит символов (по умолчанию 100 000) — это защита от случайных расходов, а не автоматизация: плагин не переводит ничего сам, лимит просто ограничивает сумму, которую можно потратить, нажимая кнопку.

Ключ хранится в базе данных сайта (опция `mlp_settings`) и никогда не выводится в HTML, JS, REST-ответы и логи (ТЗ, раздел 13) — только последние 4 символа для подтверждения «это тот ключ, что вводили». Это удобнее `.env`, но у такого хранения другой профиль риска: ключ окажется в дампе БД и в бэкапах сайта, если они не зашифрованы, — при переносе сайта или экспорте БД третьим лицам учитывайте это.

`.env` остаётся резервным способом для тех, кто предпочитает хранить ключ вне базы: `OPENAI_API_KEY`, `OPENAI_MODEL`, `OPENAI_BASE_URL` в `.env.example`. Приоритет всегда у поля в админке — `.env` используется, только если оно пустое.

**Как это работает:** рядом с полем перевода (в списке строк и в визуальном редакторе) появляется кнопка «Перевести с ИИ». Нажатие отправляет исходный текст в OpenAI и подставляет ответ в поле — **не сохраняя его**. Перевод остаётся черновиком (статус «Машинный»), пока вы не проверите его и не нажмёте «Сохранить» сами.

Своего провайдера (другой сервис вместо OpenAI) можно подключить фильтром, без правки ядра плагина:

```php
add_filter( 'mlp_translation_provider', function () {
    return new My\CustomProvider();
} );
```

Класс должен реализовать `WpMlp\Translation\ProviderInterface`.

### Если «Перевести с ИИ» падает с сетевой ошибкой

Сообщение вида `Не удалось получить перевод от OpenAI: сетевая ошибка: cURL error 28: Operation timed out after ... with 0 bytes received` значит, что запрос к OpenAI не получил ответа вовсе — ни ошибки, ни начала данных — за отведённое время. Плагин делает **до двух попыток по 45 секунд** с паузой между ними и на время самого запроса увеличивает `max_execution_time` PHP, чтобы хостинг не оборвал его раньше — если сообщение всё равно появилось, обе попытки не достучались до сервера. Дальше это не задача плагина: он честно ждал и ясно сообщил о неудаче, но не может обойти обрыв связи. Что проверить:

- **Адрес API** («Мультиязычность → Языки → Адрес API»): по умолчанию `api.openai.com` — если там стоит свой прокси/шлюз, проблема может быть в нём, а не в OpenAI;
- **Исходящие соединения хостинга**: некоторые дешёвые тарифы блокируют или сильно режут исходящий HTTPS на нестандартные адреса — спросите поддержку хостинга, проходит ли `curl https://api.openai.com` с сервера вообще;
- **Статус OpenAI**: <https://status.openai.com> — если у них сбой, ждать 30–45 секунд бессмысленно ни при каком таймауте;
- **Размер материала**: при «Перевести весь материал с ИИ» текст режется на части по ~6000 символов (`BatchChunker`) — если ошибка стабильно на одном и том же большом куске, а на маленьких строках перевод проходит, дело не в связи, а в том, что модель не укладывается в отведённое время именно на этом объёме.

Если ошибка не разовая, а стабильная — перевод в любом случае ничего не портит: строка просто остаётся черновиком без сохранённого перевода, повторная попытка безопасна в любой момент.

## Устройство

```
wp-mlp.php                  bootstrap: заголовок плагина, автозагрузчик, запуск
uninstall.php               удаление данных — только по явной галочке
src/
  Plugin.php                композиционный корень: контейнер и хуки
  Container.php             минимальный DI
  Support/                  языковые коды, хеши, нормализация текста
  Settings/                 языки сайта в одной опции wp_options
  Routing/                  язык из URL, rewrite-правила, канонический 301
  Rendering/                output buffering, DOM, извлечение, подстановка,
                            режим редактора и маркеры узлов
  Storage/                  схема БД, репозитории, объектный кэш, дневной бюджет
  Translation/              ProviderInterface, ManualProvider, OpenAiProvider
  Admin/                    «Языки», «Перевод строк», «Визуальный редактор»
  Rest/                     эндпоинты переводов и блоков
  Frontend/                 переключатель языков, hreflang и canonical
docs/technical-spec.md      полное техническое задание
PROMPTS.md                  задания по этапам
```

### Таблицы

| Таблица | Назначение |
|---|---|
| `{prefix}mlp_sources` | исходные строки: текст, хеши, вид, язык |
| `{prefix}mlp_translations` | переводы: текст, статус, автор, провайдер |
| `{prefix}mlp_occurrences` | где встретилась строка |
| `{prefix}mlp_routes` | локализованные slug (заполняется на Этапе 4) |

Уникальность строки обеспечивает колонка `uniq_hash` — SHA-256 от всех частей ключа. Составной уникальный индекс из ТЗ 6.1 содержит nullable-колонки, а MySQL считает `NULL` значения различными, поэтому дубли он бы не остановил.

### REST API

Всем эндпоинтам нужны права `manage_options` и REST-nonce.

| Метод | Адрес | Назначение |
|---|---|---|
| `GET` | `/wp-json/mlp/v1/sources/{id}` | строка и её переводы на все языки |
| `PUT` | `/wp-json/mlp/v1/translations/{id}/{locale}` | сохранить перевод |
| `DELETE` | `/wp-json/mlp/v1/translations/{id}/{locale}` | удалить перевод |
| `POST` | `/wp-json/mlp/v1/translations/{id}/{locale}/suggest` | получить перевод от ИИ, не сохраняя |
| `POST` | `/wp-json/mlp/v1/blocks` | объединить абзац в translation block |
| `DELETE` | `/wp-json/mlp/v1/blocks/{id}` | разобрать блок обратно на части |
| `GET` | `/wp-json/mlp/v1/posts/{post_id}/summary` | «Перевести весь материал»: разобрать запись, завести недостающие строки, вернуть список сегментов и границы частей |
| `POST` | `/wp-json/mlp/v1/posts/{post_id}/chunk` | перевести одну часть через ИИ, ничего не сохраняя |
| `POST` | `/wp-json/mlp/v1/posts/{post_id}/commit` | сохранить весь список одной атомарной операцией |

### Производительность

На прогретом словаре страница добавляет **2–3 SQL-запроса**, независимо от количества строк на ней: переводы забираются одним `IN`-запросом. Запись новых строк отложена на `shutdown`, то есть уже после отправки ответа. Отметка «строка ещё жива» обновляется не чаще раза в час на страницу.

Список translation blocks лежит в автозагружаемой опции, поэтому пока блоков нет, они не стоят ни одного запроса. Как только блоки появятся, разбор страницы начнёт дополнительно сериализовать и проверять каждый абзац с инлайновыми тегами — заметно это станет только на очень больших страницах.

Предпросмотр редактора работает иначе обычной страницы: он не кэшируется, отдаёт `noindex` и пишет найденные строки сразу, а не на `shutdown`, — иначе маркерам не на что было бы ссылаться.

Если на сайте есть постоянный объектный кэш (Redis, Memcached), переводы кэшируются между запросами; при сохранении перевода кэш обесценивается целиком через номер версии.

### Кэш страниц (WP Rocket, WP Fastest Cache и т.п.)

При сохранении, удалении или машинном переводе строки плагин пытается сбросить кэш готового HTML у самых распространённых плагинов кэширования — WP Rocket, WP Fastest Cache, WP Super Cache, W3 Total Cache, LiteSpeed Cache, SiteGround Optimizer, WP Engine. Без этого посетитель мог бы ещё долго видеть старую, непереведённую версию страницы: раздающий кэш плагин не знает о переводах и не спрашивает у WordPress, поменялось ли что-то в базе.

Интеграция сделана через проверку `function_exists()`/`class_exists()` по документированным функциям каждого плагина — она не тестировалась вживую на реальных установках этих плагинов, только по коду. Если после сохранения перевода страница на сайте всё равно не обновляется — проверьте, не осталась ли она в кэше вашего конкретного плагина, и вручную сбросьте его хотя бы один раз.

Для кэша, которого нет в списке (Cloudflare, Varnish, кастомный reverse-proxy), есть хук:

```php
add_action( 'mlp_purge_page_cache', function () {
    // сбросить свой кэш
} );
```

## Разработка

Рантайм-зависимостей нет, Composer нужен только для тестов.

```bash
composer install
composer test          # или vendor/bin/phpunit
```

Composer не обязателен — тесты запускаются и phar-архивом PHPUnit:

```bash
curl -sSLO https://phar.phpunit.de/phpunit-12.phar
php phpunit-12.phar
```

Тесты (`tests/`) проверяют чистую логику без загрузки WordPress: нормализацию строк, хеши, валидацию языковых кодов, разбор URL, сборку rewrite-правил, извлечение строк из DOM, подстановку перевода (включая запасной libxml-парсер), маркеры редактора, translation blocks, разбор `.env` и сборку/разбор запроса к OpenAI. Функции WordPress подменены заглушками в `tests/stubs.php`. Сетевой вызов к OpenAI не тестируется — `OpenAiRequestBuilder` (сборка payload, разбор ответа) специально вынесен из `OpenAiProvider` (сам HTTP-запрос), чтобы логику можно было проверить без мока сети.

Всё, что зависит от `$wpdb` и хуков, проверяется вручную на реальном сайте — сценарий приёмки описан в `PROMPTS.md`, раздел 9.

Если PHP локально не установлен:

```powershell
winget install PHP.PHP.8.4
```
