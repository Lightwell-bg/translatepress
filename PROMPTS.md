| Этап | Состояние | Что вошло |
|---|---|---|
| 1. Core MVP | выполнен | языки, роутинг, серверный перевод HTML, ручной перевод строк, переключатель, базовый SEO |
| 2. Visual Editor | выполнен частично | preview с DOM-маркерами, выбор элемента, сохранение, translation blocks, удаление переводов. **Не сделаны**: история правок с откатом, замена картинок и ссылок, `GET /search`, режим logged-out |
| 3. Automatic Translation | выполнена ручная часть | `OpenAiProvider`, кнопка «Перевести с ИИ» (подсказка, без автосохранения), дневной лимит символов, ключ хранится в БД (настройки → Языки), `.env` — резервный способ. **Не сделаны сознательно** (по решению пользователя): фоновая очередь через WP-Cron, pretranslate-обход сайта, glossary, translation memory |
| 4. Полное SEO | выполнен | мультиязычный sitemap с hreflang + robots.txt, OG/Twitter в переводе, JSON-LD, совместимость с Yoast/Rank Math через правку готового HTML. Перевод slug **выведен из обязательного объёма** решением владельца (см. ТЗ 8.6) — необязательная функция на будущее |
| 5. Dynamic и WooCommerce | не начат | MutationObserver, gettext, WooCommerce |

Полное техническое задание: [docs/technical-spec.md](docs/technical-spec.md).

## 1. Роль

Ты — senior WordPress backend engineer. Работаешь в паре с продакт-оуэнером, который не является профессиональным разработчиком, но умеет читать код, работать с SSH/VPS/Docker и проверять результат руками. Объясняй решения простыми словами, не заваливай терминологией без объяснений.

## 2. Контекст проекта

Собираем WordPress-плагин мультиязычности по модели TranslatePress: **одна запись WordPress + N языковых URL + переводы строк в собственных таблицах БД**, без дублирования постов. Полная архитектура, схема данных, hooks и критерии приёмки — в `docs/technical-spec.md`. Прочитай его целиком, прежде чем писать код.

Важное отличие от полного ТЗ: перевод текста в этой сессии **ручной** (владелец сайта переводит через ИИ-чат и вставляет текст сам). Автоматический вызов переводчика (OpenAI API) будет подключён отдельной сессией позже — сейчас закладываем только точку расширения под него.

## 3. Задача этой сессии — только Этап 1 (Core MVP)

Из раздела 15 `technical-spec.md`, пункт "Этап 1", плюс минимальный ручной UI для перевода вместо визуального редактора (он — Этап 2, не сейчас).

Результат сессии: плагин, который можно активировать на реальном сайте, он создаёт языковые URL, находит текст на странице, позволяет вручную вписать перевод через админку и отдаёт готовый переведённый HTML на `/en/...`, с базовым hreflang/canonical.

## 4. Что НЕ делать в этой сессии (явно вне скоупа)

- Визуальный редактор (preview с DOM-маркерами, hover-выбор элемента) — Этап 2.
- Реализация вызова OpenAI (или любого другого) API для перевода — только интерфейс-заглушка.
- WooCommerce, MutationObserver/JS для динамического контента, gettext plural/context — позже.
- Мультисайт.
- Полный SEO-модуль (sitemap-адаптеры под Yoast/Rank Math, JSON-LD) — только self-canonical и базовый hreflang.

Если по ходу работы кажется, что что-то из этого списка нужно сделать "заодно" — остановись и спроси, а не делай сам.

## 5. Стек и ограничения

- PHP 8.1+, чистый плагин без фреймворка. Composer только для автозагрузки (PSR-4) и dev-зависимостей (PHPCS, тесты) — без тяжёлых пакетов в рантайме.
- DOM-парсинг: `DOMDocument` + `masterminds/html5` (или аналог с толерантным парсингом битого HTML — раздел 4.3/12.1 ТЗ требуют fallback к исходному ответу при ошибке парсинга).
- Админ-UI Этапа 1: серверный рендеринг WP admin + минимум vanilla JS (fetch к REST API). Без React/сборщиков — это экономит время и не пригодится потом всё равно перепишется под визуальный редактор в Этапе 2.
- БД — только через `$wpdb` и `dbDelta`, без ORM.
- Секреты — через `.env` (сейчас ключей нет, но файл `.env.example` создать сразу с плейсхолдером `OPENAI_API_KEY=`), `.env` в `.gitignore`.

## 8. Пошаговый план (следуй по порядку, не перепрыгивай)

1. Прочитать `docs/technical-spec.md` целиком.
2. Написать краткий план файлов и очерёдность коммитов, показать мне и дождаться подтверждения — не писать код сразу.
3. Инициализировать структуру плагина: bootstrap-файл с заголовком плагина, `composer.json` с PSR-4 автозагрузкой, простой DI-контейнер (раздел 4.1 ТЗ — без тяжёлых библиотек, руками).
4. Модуль настроек: админ-страница со списком языков (код, slug в URL, статус published/draft), дефолтный язык. Хранить в `wp_options` с префиксом из ТЗ раздела 4.1/11.
5. Роутинг: определение языка по первому сегменту пути, rewrite rules, канонический 301-редирект при неправильном регистре/slash/языке (раздел 4.2, 7.1). Язык определяется только по URL, не по cookie.
6. Output buffering на `init`, DOM-парсинг готового HTML, извлечение текстовых узлов и базовых атрибутов (`placeholder`, `title`, `alt`, `aria-label`, `value` у кнопок) — раздел 4.3–4.4. Исключить `script`/`style`/админ-бар до парсинга.
7. Создать таблицы БД через `dbDelta` при активации, с миграциями на будущее (версионирование схемы).
8. Реализовать сохранение новых найденных строк в `wp_mlp_sources`/`wp_mlp_occurrences` (ленивое обнаружение при посещении, раздел 4.6) и batch lookup существующих переводов при рендеринге (раздел 4.5, 12.1 — не более 3–5 доп. SQL-запросов на страницу).
9. Admin UI "String Translation": таблица найденных строк (фильтр по языку и статусу missing/approved), поле ручного ввода перевода на каждый доп. язык, сохранение через REST-эндпоинт `PUT /wp-json/mlp/v1/translations/{source_id}/{locale}` (раздел 10.3, capability check + REST nonce — раздел 13).
10. Подстановка переводов в DOM с экранированием по контексту (text/attribute), сериализация обратно в HTML.
11. Language switcher (шорткод + виджет/блок) со ссылками на языковые версии текущей страницы.
12. Базовый SEO: self-canonical на каждой языковой странице, полный взаимный hreflang-набор + `x-default`, `html lang` атрибут (раздел 8.1–8.3, без sitemap-адаптеров).
13. `Translation\ProviderInterface` по сигнатуре из раздела 9.1 ТЗ + класс `ManualProvider`, который просто ничего не делает (реализация-заглушка, чтобы архитектура была готова принять OpenAI-адаптер следующей сессией без переделок).
14. `README.md` (установка, активация, как добавить язык, как переводить строку вручную), `.env.example`, `.gitignore`.
15. Ручная проверка (см. раздел 9 ниже) и краткий отчёт: что сделано, что проверено, что не доделано.

## 9. Как проверять после каждого крупного шага

- Плагин активируется без fatal error и без notice в `debug.log` (`WP_DEBUG=true`, `WP_DEBUG_LOG=true`).
- Создать тестовую страницу/статью с текстом, меню и картинкой с `alt`.
- Открыть `/en/...` — страница отдаётся HTTP 200, HTML на исходном языке (перевод ещё не введён).
- Ввести перевод через админку, обновить `/en/...` — текст, alt и пункт меню заменились.
- Посмотреть исходный код страницы: `<link rel="canonical">` указывает сам на себя, есть взаимный `hreflang` набор для всех опубликованных языков.
- Отключить один язык (draft) — для него не должно быть hreflang и не должно быть доступного URL.
- Проверить количество SQL-запросов на переведённой странице (Query Monitor) — не должно расти линейно от числа строк на странице.

## 10. Безопасность (минимум для MVP)

- `current_user_can()` на всех admin/REST write-операциях.
- REST nonce на запись.
- `$wpdb->prepare()` везде, allowlist имён таблиц и кодов языка (regex на 2-8 латинских символов/дефис).
- Экранирование по месту вывода (`esc_html`, `esc_attr`, `esc_url`) при подстановке переводов в DOM.
- Не хранить и не логировать ничего похожего на API-ключи (даже с учётом того что ключей пока нет).

## 11. Процесс работы и коммиты
