# Хранение данных wp-mlp

Техническое описание: собственные таблицы плагина, использование стандартных таблиц WordPress и связи между ними. Актуально на 09.08.2026.

## 1. Принцип

Модель — «одна запись WordPress + N языковых URL», а не дублирование постов (как в TranslatePress, в отличие от WPML/Polylang, которые заводят отдельный `wp_posts` на каждый язык):

- `wp_posts`/`wp_postmeta` хранят содержимое **только на исходном языке** (`default_locale` из настроек) и никогда не переписываются переводом — ни целиком, ни частично. Плагин нигде не вызывает `wp_update_post()`/`wp_insert_post()`/`UPDATE wp_posts` для записи перевода.
- Перевод живёт в собственных таблицах плагина, **отдельно от места, где он показан**. Строка адресуется не «полем записи A», а содержимым: одинаковый по нормализованному тексту фрагмент — от заголовка H1 до подписи к картинке в другой записи — представлен ОДНОЙ строкой словаря с одним переводом, кем бы и где бы он ни был найден.
- На дополнительном языке готовая страница подменяется на лету: `OutputBuffer` перехватывает уже отрисованный HTML, `Extractor` находит в нём переводимые фрагменты, `Translator` подставляет перевод по словарю. Оригинал в базе не тронут ни на байт.

## 2. Собственные таблицы

Префикс — `{$wpdb->prefix}mlp_*`. Список имён — allowlist в `Storage\Schema::TABLES`, наружу не подставляется ничего, кроме этих четырёх суффиксов (раздел 13 ТЗ: имя таблицы нельзя провести через `$wpdb->prepare()`, поэтому оно строится только из константы).

### 2.1 `wp_mlp_sources` — словарь исходных строк

Одна строка — один уникальный по смыслу фрагмент текста на исходном языке. Содержимое общее для всего сайта: то же самое предложение, встреченное на пяти разных страницах, — одна запись здесь, а не пять.

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | bigint PK | Внутренний идентификатор — на него ссылаются `translations`/`occurrences`. |
| `source_locale` | varchar(20) | Язык оригинала (обычно = `default_locale` сайта). |
| `kind` | varchar(32) | `text` / `attribute` / `html_block` / `seo` — вид сегмента (см. §3). |
| `source_text` | longtext | Нормализованный исходный текст — единые пробелы, без краевых отступов (`Support\Text::normalize()`). |
| `source_hash` | binary(32) | SHA-256 от `source_text` — используется отдельно (например, чтобы найти все translation blocks одним запросом по `kind='html_block'`). |
| `context_hash` | binary(32) | Зарезервировано под будущий gettext-контур (раздел 9.1 ТЗ); на сегодня всегда хеш пустой строки — ничего не различает. |
| `domain`, `gettext_context`, `plural_key` | nullable | Те же самые «на будущее» поля из раздела 6.1 ТЗ. Сегодня всегда `NULL`. |
| `uniq_hash` | binary(32) | **Единственный практический ключ идентичности строки** — см. §3. `UNIQUE KEY`. |
| `created_at`, `last_seen_at` | datetime | Когда строка впервые найдена и когда видели её в последний раз (см. §7 про «протухшие» строки). |

Почему `uniq_hash`, а не составной `UNIQUE(source_locale, kind, source_hash, context_hash, domain, gettext_context, plural_key)`, как буквально написано в разделе 6.1 ТЗ: в MySQL `NULL != NULL`, а три из семи полей — nullable. Составной уникальный индекс с NULL-полями не защищает от дублей: строка с одинаковыми значениями остальных полей и `domain = NULL` вставится сколько угодно раз. Решение, согласованное отдельно (см. `PROMPTS.md`): все семь полей ТЗ остаются в таблице как есть, но уникальность вынесена в один посчитанный `uniq_hash = SHA256(part1 + 0x1F + part2 + ... )` (`Support\Hash::ofParts()`), и именно на него вешается `UNIQUE KEY`.

### 2.2 `wp_mlp_translations` — переводы

Одна строка — один перевод одного источника на один язык.

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | bigint PK | |
| `source_id` | bigint | → `sources.id`. |
| `target_locale` | varchar(20) | Язык перевода. |
| `translated_text` | longtext, nullable | Сам перевод. `NULL`/пусто — считается отсутствующим. |
| `status` | varchar(20) | `missing` / `machine` / `review` / `approved` / `stale` / `rejected` (`Storage\TranslationStatus`). |
| `provider`, `model` | varchar, nullable | Кто перевёл (например `openai`, `gpt-4o-mini`) — пусто для ручного перевода. |
| `source_revision` | binary(32), nullable | `source_hash` оригинала на момент, когда переводили — задел на «перевод устарел» (в массовом переводе за актуальность отвечает отдельный слепок в postmeta, см. §6.2). |
| `created_by` | bigint, nullable | `wp_users.ID` автора правки. |
| `created_at`, `updated_at` | datetime | |

`UNIQUE KEY source_target (source_id, target_locale)` — у одной строки не может быть двух переводов на один язык одновременно; запись всегда идёт через `INSERT ... ON DUPLICATE KEY UPDATE` (`TranslationRepository::save()`).

### 2.3 `wp_mlp_occurrences` — где строка встречается

Одна строка — «эта строка словаря замечена вот в этом месте». Одному `source_id` может соответствовать много строк `occurrences` (одна фраза на десяти страницах — десять occurrence-записей).

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | bigint PK | |
| `source_id` | bigint | → `sources.id`. |
| `object_type` | varchar(32) | `url` (обычная отрисованная страница) или `post` (см. §4 — два независимых источника обнаружения). |
| `object_id` | bigint, nullable | `wp_posts.ID`, если место — конкретная запись/страница; `NULL` — если это архив, поиск, страница без записи (`WP_Query::get_queried_object_id()` вернул 0). |
| `url_hash` | binary(32), nullable | Хеш пути страницы (`object_type = 'url'`) — различает «та же строка, но на разных URL». `NULL` при `object_type = 'post'`. |
| `attribute_name` | varchar(64), nullable | Имя HTML-атрибута (`alt`, `content`…) для `kind = attribute`; `NULL` для текста. |
| `uniq_hash` | binary(32) | Собственная уникальность ЭТОЙ occurrence-записи — не путать с `sources.uniq_hash`! См. врезку ниже. |
| `first_seen_at`, `last_seen_at` | datetime | |

**Важно про `occurrences.uniq_hash`.** Это отдельный, СВОЙ хеш — не значение из `sources`, а составной ключ именно места использования, чтобы `INSERT ... ON DUPLICATE KEY UPDATE last_seen_at = ...` не плодил дублей при повторном показе той же страницы. Для обычной страницы (`object_type = 'url'`) он строится из `(source_id, 'url', url_hash, attribute)` — путь страницы уже часть ключа. Для массового перевода записи (`object_type = 'post'`) он обязан включать `object_id` (id самой записи) — если этого не сделать, две РАЗНЫЕ записи с одинаковым абзацем (общая фраза-заготовка) вычислят один и тот же `uniq_hash`, и вторая регистрация молча заменит первую в базе — ровно так выглядел реальный баг (`foreign_segment`, исправлен 09.08.2026, `Translation\PostOccurrenceRows`): запись, «проигравшая» коллизию, переставала подтверждать владение общим сегментом и не могла сохранить его перевод.

Индексы, кроме `uniq_hash`: `source_id` (частые JOIN на sources/translations) и `url_hash`.

`OccurrenceRepository::belongsToObject(sourceId, objectId)` — `SELECT 1 ... WHERE source_id = ? AND object_id = ? LIMIT 1` — это и есть проверка «эта строка точно из этой записи», на которой держится атомарность массового перевода (§7).

### 2.4 `wp_mlp_routes` — зарезервирована, не используется

Таблица создаётся (`Schema::install()`), но ни один класс плагина её не читает и не пишет. Задел под перевод slug (раздел 8.6 ТЗ) — решением заказчика выведен из обязательного объёма текущих этапов (см. `PROMPTS.md`, «Этап 4»). Столбцы (`object_type`, `object_id`, `locale`, `source_slug`, `translated_slug`, `path_hash`, `status`) соответствуют разделу 6.4 ТЗ на будущее.

Таблицы `jobs`, `usage`, `logs`, `glossary`, `redirects` из раздела 6.5 ТЗ не создаются вовсе: дневной лимит символов на перевод и хранится проще — см. §6.3 про `wp_options`.

## 3. `uniq_hash` — идентичность строки словаря

`Support\Hash::ofParts([locale, kind, source_hash, context_hash, domain, gettext_context, plural_key])`, порядок фиксирован. Части `domain`/`gettext_context`/`plural_key` сегодня всегда пустые — единственное, что реально различает строки: **язык**, **вид сегмента (`kind`)** и **сам нормализованный текст**.

Из этого прямо следует правило «одинаковый текст → один и тот же перевод», но с одной оговоркой: раз `kind` — часть хеша, одинаковый текст в РАЗНОМ виде (обычный текстовый узел vs. значение HTML-атрибута vs. поле JSON-LD) по умолчанию даёт РАЗНЫЙ `uniq_hash` — это специально: `alt` картинки и случайно совпавший по тексту абзац не должны насильно делить один перевод (см. `ExtractorTest::testTextAndAttributeGetDifferentHashes`).

Из этого правила есть узкое, явное исключение — заголовок записи. `og:title`/`twitter:title` (meta-атрибут) и JSON-LD `headline` при подсчёте хеша **намеренно приравниваются к обычному тексту** (`hashKind` в `Extractor::makeSegment()`), когда их содержимое совпадает с заголовком H1/`<title>`. Без этого исключения один и тот же заголовок статьи мог получить четыре независимо переведённых, расходящихся друг с другом варианта в разных местах страницы (исправлено 09.08.2026, «доработка SEO/GEO»). Итоговый `kind`, под которым строка хранится и показывается в «Переводе строк», при этом не меняется — подменяется только хеш-идентичность, не то, что видно в интерфейсе.

При коллизии `uniq_hash` НЕСКОЛЬКИХ сегментов на одной странице (после hashKind-исключения выше это стало возможно чаще, чем раньше) `Rendering\SegmentDeduplicator::deduplicate()` решает, какой из них — «представитель» для записи новой строки в `sources`: по умолчанию первый по порядку в документе, но SEO-сегмент (JSON-LD-поле или `content` у meta) побеждает простой текст независимо от порядка — иначе объединённый заголовок почти всегда получал бы `kind = text` (`<title>`/H1 в разметке раньше JSON-LD-скрипта) и переставал находиться фильтром «Тип → SEO/GEO» в «Переводе строк».

## 4. Два источника обнаружения строк, один словарь

Строки в `sources`/`occurrences` появляются одним из двух путей — независимо, но **по общей схеме хеширования**, поэтому перевод, найденный одним путём, сразу виден другому.

**А. Обычная страница** (`Rendering\Extractor` → `Rendering\Translator`). Работает по уже ОТРИСОВАННОМУ HTML: обходит DOM, находит текстовые узлы и переводимые атрибуты, ищет перевод по `uniq_hash`, подставляет, откладывает запись новых строк на `shutdown` (чтобы не удлинять ответ посетителю). `object_type = 'url'`, `object_id` = id записи (если это она) или `NULL`, `url_hash` = хеш пути текущей страницы.

**Б. «Перевести весь материал с ИИ»** (`Rendering\PostContentExtractor` → `Rest\PostTranslationController`). Работает по СЫРЫМ полям записи (`post_title`/`post_excerpt`/`post_content`), а не по отрисованной странице — иначе комментарии Gutenberg `<!-- wp:... -->` не пережили бы рендер блоков (ядро их вырезает). Тем же самым `Extractor`, значит с тем же способом считать `uniq_hash`. `object_type = 'post'`, `object_id` = id записи, `url_hash` всегда `NULL` — привязки к конкретному показу страницы тут нет, только к записи.

Перевод сохраняется в ОДНУ И ТУ ЖЕ строку `translations` независимо от того, каким из двух путей его нашли и сохранили: `source_id` — общий, привязки «откуда именно» на самом переводе нет, она есть только у occurrence-записей.

## 5. Связи между таблицами

Никаких физических `FOREIGN KEY` — обычная практика для плагинов WordPress (`dbDelta` их не умеет, да и ядро WP ими не пользуется). Связи только логические, через обычные int/binary-колонки и код приложения:

```
wp_posts (стандартная, только читается)
    │  id
    │
    ├──────────────◄── wp_mlp_occurrences.object_id   (когда object_type = 'post'/'url' и это конкретная запись)
    │
    └──────────────◄── wp_postmeta.post_id             (_mlp_translated_segments_{locale} — см. §6.2)

wp_mlp_sources
    │  id
    │
    ├──────────────◄── wp_mlp_translations.source_id   (1 источник : N переводов, по одному на язык — UNIQUE(source_id, target_locale))
    │
    └──────────────◄── wp_mlp_occurrences.source_id    (1 источник : N мест использования)

wp_mlp_translations.(source_id, target_locale)  — уникальная пара, взаимно однозначно источник+язык → перевод
wp_mlp_occurrences.(source_id, object_id)        — не уникальная пара сама по себе (см. §2.3), но именно
                                                    её проверяет belongsToObject() перед тем, как разрешить
                                                    сохранить перевод строки в контексте конкретной записи
```

Практическое следствие отсутствия физических FK: удаление записи WordPress (`wp_posts`) НЕ каскадно удаляет её `occurrences`/`sources`/`translations` — они просто перестают на что-то указывать (`object_id` продолжает существовать как число) и «протухают» тихо, без ошибок (см. §7).

## 6. Использование стандартных таблиц WordPress

### 6.1 `wp_posts` — только чтение содержимого

Читается через `get_post()`, `get_permalink()`, `get_post_modified_time()`, `get_the_title()` и т. п. — обычные API ядра, не прямой SQL. **Ни разу не изменяется** плагином (grep по `wp_update_post|wp_insert_post|UPDATE.*wp_posts` в `src/` — ноль совпадений). Источник дат для `lastmod` карты сайта и источник самого текста для перевода, но не хранилище перевода.

### 6.2 `wp_postmeta`

Единственный ключ, который плагин пишет и читает сам:

- `_mlp_translated_segments_{locale}` — список hex-хешей строк, переведённых при ПОСЛЕДНЕМ «Перевести весь материал с ИИ» для этой записи на этот язык (`Storage\PostTranslationSnapshot`). Отдельной таблицы под это не заводится намеренно: сам `uniq_hash` уже и есть идентичность абзаца — если текст не менялся, при повторном разборе выйдет тот же хеш и найдётся тот же перевод. Слепок нужен только для узкой задачи «пометить именно то, что изменилось с прошлого раза», а не всё огулом.

Читаются (никогда не пишутся) ключи чужих SEO-плагинов — только для решения «включать ли эту страницу в карту сайта» (`Frontend\SitemapRobotsMeta`), без всякой зависимости от их внутреннего API в остальном коде:

- `_yoast_wpseo_meta-robots-noindex` (Yoast SEO)
- `rank_math_robots` (Rank Math)
- `_seopress_robots_noindex` (SEOPress)

### 6.3 `wp_options`

Одна опция на смысловой блок, не десяток отдельных (ТЗ 4.1/11 — «одна автозагружаемая опция вместо множества»):

| Опция | Что хранит |
|---|---|
| `mlp_settings` | Все настройки плагина одним массивом: языки, дневной лимит символов, ключ/модель/адрес OpenAI, флаг «удалять данные при удалении плагина», исключённые из карты сайта слаги и т. д. (`Settings::defaults()`/`sanitize()`). |
| `mlp_db_version` | Версия схемы БД — для `Schema::maybeUpgrade()` при обновлении плагина копированием файлов (хук активации в этом случае не срабатывает). |
| `mlp_cache_version` | Счётчик, растущий при каждом сохранении перевода — без адресной инвалидации кэша: старые ключи объектного кэша просто перестают использоваться, когда версия в них меняется (§6.4). |
| `mlp_block_hashes` | Кэш списка хешей translation blocks (`kind = 'html_block'`) — чтобы не ходить в БД за этим списком на каждой странице. |
| `mlp_usage_{Y-m-d}` | Сколько символов ушло в OpenAI за конкретный день — отдельная опция на КАЖДЫЙ день, вчерашняя удаляется сразу после создания сегодняшней (`UsageTracker`). Не отдельная таблица `wp_mlp_usage` из раздела 6.5 ТЗ — при ручном запуске кнопкой (не очередью) объём не оправдывает таблицу; если появится фоновая очередь, это первое, что стоит заменить. |

### 6.4 Объектный кэш (`wp_cache_*`)

Без постоянного бэкенда (Redis/Memcached) живёт в пределах одного запроса — и даже так полезен: одинаковые строки на странице ищутся один раз. С постоянным бэкендом кэш переживает между запросами.

| Группа | Что | Инвалидация |
|---|---|---|
| `mlp_translations` | «строка+язык → перевод», включая закешированное отсутствие перевода (иначе непереведённая строка ходила бы в БД на каждый показ). TTL 12 часов. | Через `mlp_cache_version` в самом ключе — версия растёт при `TranslationCache::flush()`. |
| `mlp_sitemap` | Готовый XML карты сайта целиком. TTL 1 час. | Тот же `mlp_cache_version` в ключе. |
| `mlp_translated_posts` | Список id переведённых записей для скрытия непереведённых из перечислений (`UntranslatedFilter`). TTL 1 час. | Тот же `mlp_cache_version` в ключе. |

`TranslationCache::flush()` дополнительно зовёт `PageCachePurger::purgeAll()` — сброс стороннего page cache (WP Super Cache, W3TC, WP Rocket, LiteSpeed и т. п., каждый через `function_exists`/`class_exists`), потому что готовый HTML на диске/в их кэше про изменение перевода не узнает сам.

### 6.5 Transients

- `mlp_touched_{urlHash}` (TTL 1 час) — не «обновлять записи о месте использования» на каждый показ страницы, а не чаще раза в час: иначе строка меню, впервые найденная на одной записи, никогда не подтвердила бы себя как «общий элемент сайта», если её всегда трогать только по одной записи.
- `mlp_settings_errors_{userId}` (TTL 1 минута) — ошибки формы настроек между redirect после сохранения и следующей отрисовкой страницы; в БД дольше минуты не нужны.

## 7. Целостность операций

Прямых FK нет (§5), поэтому целостность держится на дисциплине кода, а не на СУБД:

- **Массовый перевод записи** — двухслойная атомарность. Сначала `Translation\PostCommitValidator::validate()` проверяет ВЕСЬ присланный пакет целиком, ни разу не трогая `$wpdb` на запись: неизвестный/чужой (см. §2.3 про `belongsToObject`)/задвоенный `uniq_hash`, испорченный шорткод — любая находка отклоняет пакет целиком, «ни одна строка». Только полностью чистый пакет идёт дальше — одной SQL-транзакцией (`START TRANSACTION`/`COMMIT`/`ROLLBACK` в `PostTranslationController::writeAtomically()`), на случай отказа самой БД посреди записи.
- **«Протухшие» строки не удаляются активно.** Ни `sources`, ни `occurrences` не чистятся автоматически, когда текст со страницы пропадает или запись удаляется/переписывается: `last_seen_at`/`first_seen_at` просто перестают обновляться. Единственное исключение — translation blocks (`kind = 'html_block'`): их можно удалить явно через редактор блоков (`SourceRepository::deleteWithTranslations()`), это осознанно единственный путь удаления строки из словаря. Практическое следствие: «Перевод строк» может показывать строки, которых уже нигде нет на сайте, — это не баг, а стоимость модели «содержимое, не удалённая ссылка» (см. обсуждение в истории проекта про карту сайта и «почему это в непереведённых»).
